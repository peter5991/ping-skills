# Ping Skill：三视角头脑风暴

一个强制"先理解、再发散、后收敛"的头脑风暴流程。

## 核心原则

1. **绝不假装理解。** 未获得用户对《理解确认书》的明确确认，禁止进入头脑风暴阶段。宁可多问一轮，不可猜测用户意图。
2. **每个视角都是真讨论。** 三视角逐个输出，每个视角之后必须暂停，给用户补充、纠正、反驳的机会，再进入下一个视角。禁止一次性输出全部三视角的报告式罗列。
3. **反向视角是建设性批判。** 不只找毛病，每个被指出的问题必须附带修复方案或规避路径。

## 阶段一：意图澄清（硬性门禁）

收到用户的问题/议题后：

1. 提出澄清问题，围绕四个维度：
   - **真实目标**：用户到底想解决什么？表面问题之下的动机是什么？
   - **约束条件**：时间、资源、技术、边界——哪些是不可动的？
   - **成功标准**：什么样的结果算"这次头脑风暴有价值"？
   - **已排除方向**：用户已经否定过什么？为什么？
2. 收到回答后，输出《理解确认书》：

   ```
   ## 理解确认书
   - 我理解的问题：……
   - 问题边界：……（什么在范围内、什么不在）
   - 约束条件：……
   - 成功标准：……
   - 我不确定/仍需澄清的点：……（如有）
   ```

3. **等待用户明确确认**（如"确认"、"对"、"可以开始"）。
   - 用户纠正 → 更新确认书，再次请求确认。
   - 用户确认 → 进入阶段二。
4. 若用户回答中暴露概念模糊、假设未经检验，主动建议："这里有个点值得深入追问，要不要启动苏格拉底追问？"（见"深化模块"）

## 阶段二：三视角头脑风暴

按顺序进行，**每个视角输出后必须暂停**，等待用户回应（补充/纠正/跳过）再进入下一个：

### 视角 1：正向（支持者）
- 这个命题为什么可行？有哪些可行路径？
- 它的核心优势是什么？如何放大？
- 最有希望的 2-3 个方案方向。

### 视角 2：中立（分析师）
- 事实清单：目前已知的确切信息。
- 未验证的假设：当前讨论建立在哪些未经检验的前提上？
- 信息缺口：还缺什么数据/信息才能下判断？

### 视角 3：反向（建设性批判者）
- 失败路径：这件事最可能因为什么失败？
- 错误前提：哪些假设可能是错的？
- **每个问题必须附带**：修复方案或规避路径。

## 阶段三：收敛

输出《综合建议》：

```
## 综合建议
### 强信号方向（三视角共同验证）
- ……
### 高风险方向（反向视角否决/标记）
- ……（含对应缓解措施）
### 残留分歧点
- ……（需要用户自己决策的部分）
### 建议的下一步行动
- ……
```

## 阶段四：结构化落地（可选）

当《综合建议》产出的是一个**新项目 / 新方向**，且用户表示要开始动手时，主动提议："要不要我把这个项目按标准结构搭建起来？"

获得用户确认后，按以下流程执行：

### 标准目录结构（Agent 中立）

```
<project-root>/
├── README.md               # 项目说明
├── AGENTS.md               # Agent 使用指南与约定（按所用 Agent 的习惯改名：CLAUDE.md / CODEX.md / GEMINI.md 等）
├── .gitignore
├── .env.example            # 环境变量示例
├── agent.config.json       # Agent 配置（模型、权限、路径；按所用 Agent 的实际配置文件名调整）
├── package.json
├── scripts/                # 脚本目录
│   ├── run_agent.sh
│   ├── init_project.sh
│   └── deploy.sh
├── commands/               # 自定义命令
│   ├── analyze.md
│   ├── dashboard.md
│   └── report.md
├── skills/                 # Skill 技能目录
│   ├── data-analysis/SKILL.md
│   ├── visualization/SKILL.md
│   └── nlp/SKILL.md
├── agents/                 # Agent 智能体目录
│   ├── data-agent.md
│   ├── research-agent.md
│   └── report-agent.md
├── memory/                 # 记忆与上下文
│   ├── rules.md
│   ├── decisions.md
│   └── context.json
├── logs/                   # 操作与修改记录
│   ├── operations.log      # 操作流水：谁在何时做了什么操作
│   └── changes.md          # 修改记录：文件/功能的变更历史与原因
└── output/                 # 输出目录（不入库）
    ├── reports/
    ├── charts/
    └── logs/
```

### 执行步骤

1. **确认根目录**：询问或推断项目根路径。
2. **确认目标 Agent**：问用户这个项目主要给哪个 Agent 用，据此调整 `AGENTS.md` 与配置文件的命名（如 Claude Code → `CLAUDE.md`，Codex → `CODEX.md`）。
3. **创建目录**：一次性创建所有目录（含 `output/` 的三个子目录）。
4. **生成根配置**：按顺序创建 `README.md`、`AGENTS.md`（或对应命名）、`.gitignore`、`.env.example`、`agent.config.json`、`package.json`。
5. **生成脚本**：`scripts/` 下三个 `.sh` 文件，均带 `set -e` 与可执行说明。
6. **生成命令模板**：`commands/` 下三个 `.md`，含 frontmatter（description）与参数/步骤/示例。
7. **生成技能与智能体**：`skills/*/SKILL.md` 与 `agents/*.md` 骨架文件。
8. **生成记忆文件**：`memory/rules.md`（项目规则）、`memory/decisions.md`（决策记录）、`memory/context.json`（上下文）。
9. **生成日志文件**：`logs/operations.log`（操作流水，格式：`[时间] [操作者] 操作内容`）、`logs/changes.md`（修改记录，格式：`## 日期` + 变更文件 + 变更原因）。
10. **初始化 .gitignore**：忽略 `node_modules/`、`.env`、`output/` 产物（`logs/` 默认入库，便于追溯）。

### 设计原则

- **关注点分离**：配置、脚本、命令、技能、智能体、记忆、输出各自独立。
- **可扩展性**：skills 与 agents 采用「子目录 + 定义文件」模式，便于新增能力。
- **上下文持久化**：规则与决策写入 `memory/`，跨会话保持一致。
- **声明式配置**：命令与技能用 Markdown 定义，降低使用门槛。
- **可追溯性**：Agent 每次对项目的操作与修改都应追加到 `logs/`（操作流水进 `operations.log`，变更说明进 `changes.md`），保证历史可审计。

### 可选变体

- `--minimal`：只创建根配置 + `scripts/` + `output/`。
- `--with-tests`：额外创建 `tests/` 目录。
- `--lang=python`：用 `pyproject.toml` 替代 `package.json`，脚本改为 `.py`。

## 深化模块：苏格拉底式追问（可随时插入）

**触发方式**：用户在任意时刻说"深入追问"、"苏格拉底"、"再挖一层"等；或 AI 在发现讨论薄弱点时主动提议。

**执行规则**：
- 根据当前讨论的薄弱点，从六类问题中**选取最相关的 1-2 类**发起追问，禁止机械地六类全问。
- 追问获得新信息后，带着新信息回到三视角流程，重新检验受影响的部分。
- 追问结束后更新《综合建议》。

**六类问题库**：

### 1. 厘清定义与概念
- 你为什么这么说？
- 这个到底是什么意思？
- 这个与我们所讨论的有什么关系？
- XX 的本质是什么？
- 我们对于 XX 都了解哪些？
- 你能举个例子吗？
- 你是指 XX 还是 YY？
- 你能换个说法吗？

### 2. 探究假设与前提
- 除此之外，我们还有什么假设？
- 你好像是假设了……？
- 你为什么如此假设？
- 请解释你为什么……？
- 你怎样证明或反对该假设？
- 如果发生了……，又会怎样？
- 你同意还是反对……？

### 3. 探究理由与证据
- 为什么会发生这种情况？
- 你怎么知道这个的？
- 演示给我看……？
- 你能给我举个例子吗？
- 这些理由足够充分吗？
- 如果要反驳的话，怎样做？
- 我怎么能确认他所说的是真实的？
- 为什么？为什么？为什么？（递进追问三个以上"为什么"）
- 你有什么证据支持？

### 4. 质疑观点与视角
- 另一种看待此问题的方式是……，这听起来有道理吗？
- 其他看待该问题的角度是什么？
- 为什么……是必要的？
- 谁是利益相关方？
- XX 和 YY 的区别是什么？
- XX 和 YY 的相同点是什么？
- 为什么……更优？
- XX 的优点和缺点是什么？
- 如果你把 XX 和 YY 比较，又会怎样？
- 你如何从另一个角度看待此事？

### 5. 探究后果与影响
- 这样的话，然后呢？
- 这个假设的后果是什么？
- 这个会怎样影响……？
- 为什么……是重要的？
- 最好的结果是什么？为什么？

### 6. 质疑问题本身
- 你提的这个问题有什么意义？
- 为什么这么问？
- 我还有其他问题吗？

## 反模式（禁止行为）

- ❌ 跳过澄清阶段，直接开始输出观点。
- ❌ 把三视角一次性全部输出，不给用户插入的机会。
- ❌ 反向视角只批判不给修复方案。
- ❌ 苏格拉底追问时六类问题流水账式全问。
- ❌ 收敛时含糊其辞，不明确标注哪些是强信号、哪些是高风险。
- ❌ 未经用户确认就擅自创建项目目录结构。
